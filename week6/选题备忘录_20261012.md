## 候选方向（按评估矩阵排序）

### 候选 1（主选）：csrc/ 自研量化 GMM/MoE kernel 性能优化

- **是什么**：`csrc/gmm/`（grouped_matmul_swiglu_quant、_v2、weight_nz_tensor_list、gmm_dequant_situ_quant）与 `csrc/moe/`（dequant_situ_quant、dequant_swiglu_quant、swiglu_group_quant 等）是**仓库自研 AscendC kernel**，op_host tiling + op_kernel 全部在仓库内可直接改。
- **为什么对口**：量化 GMM + 融合 + tiling 正是 WeightQuantBatchMatmulV2 的同构问题（小 M decode、分组矩阵乘、NZ 布局、L2 命中）；方法论（bound 分界模型、balanceRate 剪枝、手工流水线）可直接迁移。
- **可量化性 ×3**：有 nightly 单算子 e2e 测试（`tests/e2e/nightly/single_node/ops/singlecard_ops/test_grouped_matmul_swiglu_quant.py` 等），microbenchmark 现成。
- **影响面 ×2**：w8a8/w4a8 量化 MoE 模型的主链路（GLM5-w4a8、Kimi-K2.5/K3-W4A8、DeepSeek 系列）。
- **工作量 ×2**：需先 profiling 找到具体慢 shape（Day 38-40 的工作）；两周可闭环单个 kernel 的 tiling 优化。
- **风险**：需要 Atlas A2 实机（公司环境）；需先确认目标 kernel 当前效率 η（若已达 85%+ 则换目标）。
- **验证项**：Day 37 基线时用 msprof 跑一遍目标 kernel，看 cube 利用率/带宽利用率，决定具体攻哪个。

### 候选 2（备选/可能做大）：fp8_block 在非 950 硬件上的 BF16 fallback 消除

- **是什么**：`vllm_ascend/quantization/methods/w8a8/fp8_block.py:19-34, 259` —— block-wise FP8 在非 950 硬件（含 910B A2）上**无法走量化 matmul**，整块权重 dequant 成 BF16 再走 `unquantized_gemm`：显存翻倍 + 失去量化算力收益。官方文档明确 "per-tensor/per-channel FP8 has no Ascend execution path yet"。
- **为什么有价值**：DeepSeek 系官方 checkpoint 就是 block FP8，这是 A2 上跑 DS 模型绕不开的痛；**搜索确认当前无任何 open PR 在做这件事**。
- **风险（高）**：取决于 CANN `QuantMatmul`/`npu_weight_quant_batchmatmul` 是否支持 block-wise（128×128）scale——这是**闭源边界问题**，Day 37 必须先用小脚本验证 `torch_npu.npu_quant_matmul` 是否接受 block scale；不支持则只能自己做"分块 dequant + int8/fp8 混合 GEMM"编排，工作量翻倍。
- **降级形态**：如果完整路径做不了，可以做"权重一次性 dequant 改为按层流式 dequant 复用 buffer"这类内存优化，依然有明确收益。

### 候选 3（练手首 PR）：w8a8_dynamic.py:282 NZ 强制格式转换消除

- **是什么**：`quantization/methods/w8a8/w8a8_dynamic.py:282-286` 有 TODO：`npu_grouped_matmul_swiglu_quant` 只支持 NZ 权重，被迫每次/加载时做 `npu_format_cast(ACL_FORMAT_FRACTAL_NZ)`。
- **切入点**：让转换发生在权重加载期而非热路径，或让自研 gmm kernel 直接吃 ND 输入。
- **定位**：工作量小、链路清晰，适合作为第一个 PR 熟悉流程（DCO、CI、review 节奏），**不等候选 1 出结果就可以先做**。

### 候选 4（观察项）：topk_topp 采样 kernel 性能回归（issue #14705，open）

- MRV2 全功能采样场景 `_topk_topp_kernel` 是 device 侧热点（Qwen3-8B 复现参数齐全）。
- 若 vllm-ascend 侧无对应 kernel（走 torch 组合算子），可以在 csrc/ 实现 AscendC topk_topp 融合 kernel——纯 kernel 工作、对口、有现成 issue 背书。
- **验证项**：先确认该 kernel 当前在 NPU 上的实现路径（torch_npu 组合 or 仓库自研），判断可改边界。

## 决策

> **2026-10-12 更新：硬件确认为 Atlas A5（950DT），按此调整：**
> - **候选 2 划掉**：950 上 block FP8 已走 MXFP8 重量化 + 原生 npu_quant_matmul（fp8_block.py 文档串确认），BF16 fallback 只存在于老硬件，无 A2 则无法验证。
> - **候选 1 注意 950 特殊性**：`csrc/moe/` 的 grouped_matmul_situ_quant、situ_mx_quant 在 ascend950 上被 CMake 显式排除；950 量化格式（MXFP8/hifloat8/float4_e2m1fn_x2/e8m0 scale）是新开发区，`quantization/utils.py:31` 有 GMM dtype 过滤 TODO。选题前必须在 issue/PR 确认无人在做。
> - 950 与个人背景（910B/960/1952）同架构族，arch35 kernel 可读性有优势。

**主线：候选 1（自研量化 GMM kernel 优化，950 路径）**，Day 37 基线 profiling 后锁定具体 kernel + shape；
**并行练手：候选 3** 作为第一个 PR；
**候选 4** 若候选 1 profiling 发现效率已高，则转候选 4。
