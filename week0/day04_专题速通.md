## 专题一：量化（2h，你的主场）

### 骨架知识

**按量化对象分类**：

| 方案 | 权重 | 激活 | 典型精度损失 | 主要收益 |
|---|---|---|---|---|
| W8A8（INT8/FP8） | 8bit | 8bit | 极小 | 计算 + 访存双赢 |
| W4A16（GPTQ/AWQ） | 4bit | 16bit | 小 | 访存省 4×，decode 加速明显 |
| FP8 W8A8 | FP8 | FP8 | 极小（H100 原生支持） | 计算翻倍 + 访存减半 |
| KV cache FP8/INT8 | — | — | 小 | KV 显存减半，并发翻倍 |

**按粒度分类**（粒度越细越准，开销越大）：per-tensor < per-channel < per-group/block-wise（如 128×128 block，DeepSeek 风格）

**激活为什么难量化**：激活有 outlier 通道（少数通道幅值大几个数量级），per-tensor 量化被 outlier 拖垮 → SmoothQuant 把难度从激活"搬"到权重；AWQ 保护 1% 的 salient 权重通道。

### 必考题：量化对 TTFT 和 TPOT 的影响分别是什么？

- **TPOT（decode）**：memory-bound，时延 ≈ 权重字节数/带宽 → W4A16/FP8 几乎线性加速 decode。**收益最大的地方**
- **TTFT（prefill）**：compute-bound → 只有"计算也走量化"的方案（W8A8/FP8）才受益；W4A16 的 prefill 反而可能变慢（dequant 开销 > 访存节省）
- **结论模板**："量化方案的选择要看 SLO 落在哪——decode 敏感选 W4A16 性价比高，全面收益选 FP8 W8A8"

### ⚡ 昇腾对照叙述（今天最重要的产出，写 200 字背熟）

> "我在昇腾做 WeightQuantBatchMatmulV2 的优化，本质问题和 GPU 量化 GEMM 完全同构：decode 场景 M 小、访存 bound，所以我做 AL1/BL1 全载把权重搬运从 O(n·A) 降到 O(A)；tiling 搜优用访存/计算 bound 分界模型选 baseM/baseN。到了 GPU/vLLM 语境，这套模型就是 roofline——FP8 GEMM 的选型、KV cache 量化的收益估算，我是用同一套 bound 分析做的。"

### A4 卡片要点

方案对比表 + outlier 问题一句话 + TTFT/TPOT 影响结论 + 对照叙述。

## 专题二：Speculative Decoding（1.5h）

### 骨架知识

**原理一句话**：decode 是访存 bound，一次前向算力大量闲置 → 用便宜的方式"猜" k 个 token，大模型**并行验证**（一次前向同时算 k 个位置的 logits），接受其中最长的合法前缀。数学上可证明输出分布与原始自回归**完全一致**（无损加速）。

**三条路线**：

| 路线 | 草稿来源 | 特点 |
|---|---|---|
| Draft model | 同家族小模型（如 7B 给 70B 打草稿） | 通用，但要维护两个模型 |
| MTP（Multi-Token Prediction） | 大模型自带的多 token 预测头（DeepSeek-V3 风格） | 无需外挂模型，接受率高 |
| EAGLE / EAGLE-3 | 轻量草稿头复用大模型特征 | 接受率高，工程成熟，vLLM 主推 |

**收益公式**（能推）：每步期望产出 = 接受率 p 下接受 k 个草稿的期望 + 1 ≈ (1−p^(k+1))/(1−p)；代价是每步时延增加（验证 k 个 token + 草稿开销）。**净收益 = 每步 token 数 × 单步时延变化**，接受率低时后者主导 → 负收益。

### 失效模式（必背）

- 开放式生成/高温度采样：接受率可能只有 20-40% → 吞吐反而下降
- 大 batch 场景：batch 大了 decode 已接近 compute-bound，验证 k 个 token 的额外计算变成真实开销 → **投机解码是小 batch/低并发专属优化**
- 代码补全/模板化输出接受率 70-90% → 最甜场景

### A4 卡片要点

原理图（草稿→并行验证→接受前缀）+ 三路线表 + 收益公式 + 失效模式三条。

## 专题三：P/D 分离（2h，专家岗区分度最高）

### 骨架知识：为什么分

1. **硬件特性相反**（Day 1 结论）：prefill 要算力，decode 要带宽——同实例混跑，资源配置只能折中
2. **SLO 互相干扰**：长 prompt 的 prefill 顶住 decode → TPOT 尖峰（chunked prefill 只能缓解不能根除）
3. **伸缩粒度不同**：流量涨 2 倍，prefill 和 decode 需要的扩容比例不一样

### 怎么做：两种形态

| 形态 | KV 传输 | 适用 |
|---|---|---|
| 同节点分离 | NVLink（微秒级，直接点对点 DMA） | 单机 8 卡内划分 prefill/decode 角色 |
| 跨节点分离 | RDMA + 分层流水（逐层传 KV，与下一层计算重叠隐藏传输时延） | 大规模集群，P 实例和 D 实例独立伸缩 |

**传输是核心难点**：一个 8K prompt 的 KV 有几 GB（回忆 Day 1：70B 每 token 320KiB × 8K ≈ 2.5GB），跨节点传输必须和计算流水重叠，否则 TTFT 被打爆。

### 三个系统（知道设计差异即可）

- **Mooncake（月之暗面）**：KV cache 中心化池——把集群所有空闲显存/内存组成全局缓存池，prefix cache 跨实例共享，P/D 角色弹性
- **NVIDIA Dynamo**：官方分离式方案，KV-aware 路由 + 分层 offload（GPU→CPU→SSD）+ 按负载自动调整 P/D 比例
- **llm-d**：Kubernetes 原生的分离推理框架，红帽/Google 等共建，强调云原生调度

### 必考题：P/D 分离什么时候不值得做？

- 流量小，单实例就够：引入传输开销纯亏
- prompt 都很短：prefill 占比小，分了没收益
- 网络差的环境：跨节点传输成本超过收益

### A4 卡片要点

分离三动机 + 两形态表 + 传输隐藏手法 + 三系统一句话 + 失效场景。

## 专题四：分布式并行（1h，概念级）

### 骨架知识

| 并行方式 | 切什么 | 通信 | 什么时候用 |
|---|---|---|---|
| TP（张量并行） | 单层内切权重/头 | 每层 2 次 all-reduce | 单卡放不下 / decode 带宽不够（聚合多卡 HBM 带宽） |
| PP（流水并行） | 按层切段 | 层间点对点 | 跨节点扩展（通信量小，适合慢互联） |
| EP（专家并行） | MoE 的 expert 切到不同卡 | all-to-all | MoE 模型（DeepSeek 类） |

**经验法则（高频题第 7 题素材）**：
- **"能单卡放下就别上 TP"**：TP 每层都有 all-reduce，卡间走 NVLink 才划算；TP 跨节点（走 IB/RoCE）通信直接吃光收益
- TP 的 decode 收益逻辑：k 卡 TP → 每卡权重 1/k → 每卡读取量 1/k，但聚合带宽近 k 倍 → decode 近似加速 k 倍，**减去通信开销**。小 batch 时通信占比小、收益好；batch 大了逐渐 compute-bound，TP 边际收益递减
- EP 的坑：expert 负载不均（hot expert）→ 需要动态负载均衡

### A4 卡片要点

三方式表 + "别乱上 TP"法则 + TP decode 收益推导 + EP 负载不均。
