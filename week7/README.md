## Day 43：完整 Benchmark 前后对比

### 上午：设计可复现的 benchmark 方案

性能对比最大的坑是**不可复现**——面试官一句"你这个提升是不是抖动？"就答不上来。对比实验必须控制变量：

- **固定不变的量**：
  - vLLM 版本（commit hash 记录进对比表）、模型与 checkpoint、量化配置
  - 服务器启动参数（完整 `vllm serve` 命令原样保存为脚本）
  - 压测数据集（固定随机种子生成）、并发数序列、request rate
  - GPU 频率状态：跑之前 `nvidia-smi -lgc` 锁频（或至少确认没有降频），记录 `nvidia-smi -q -d CLOCK` 输出
- **随机化的量**：每轮压测的请求顺序（用不同 seed 跑 3-5 轮取均值±标准差）
- **轮次协议**：每轮先 warmup（预热的请求不计入统计），然后正式采集；轮间冷却 30s 防止热节流
- **统计口径**：所有指标报 p50/p99 + 均值±方差；提升百分比用均值算，但必须附方差说明显著性（若方差大于提升幅度的 1/3，结论要谨慎）

### 下午：跑基线与优化版

- 基线（优化前 commit）与优化版（当前分支）各跑完整矩阵：
  - decode 密集场景（短 prompt + 长输出）：看 TPOT
  - prefill 密集场景（长 prompt + 短输出）：看 TTFT
  - 混合场景：看 goodput（SLO 达标率下的吞吐）
- 用 `vllm bench serve` 固定参数模板：

```bash
# 基线版
git checkout <baseline-commit>
bash benchmark/run_suite.sh --tag baseline

# 优化版
git checkout <optim-branch>
bash benchmark/run_suite.sh --tag optim
```

- 输出统一为一张**前后对比表**（这张表就是 PR 和简历的数据来源）：

| 场景 | 指标 | baseline（均值±σ） | optimized（均值±σ） | 提升 |
|---|---|---|---|---|
| decode 密集 | TPOT p99 (ms) | 23.4 ± 0.8 | 19.1 ± 0.5 | -18.4% |
| prefill 密集 | TTFT p99 (ms) | 812 ± 31 | 798 ± 28 | -1.7%（不显著） |
| 混合 | goodput (tok/s @SLO) | 1240 | 1490 | +20.2% |

## Day 44：边界 Case 与精度验证

### 边界 case 清单（结合你的昇腾算子经验）

你做 WeightQuantBatchMatmulV2 时处理过 M≤256 decode、窄 N、尾块等场景——把这套边界思维迁移到项目 A：

- [ ] **shape 边界**：最小输入（M=1 单 token decode）、极大 batch（压到 `max_num_seqs` 上限）、尾块不整除（如 N=257 对齐到 256 的余量）
- [ ] **dtype 边界**：涉及量化的改动要在 BF16/FP16/INT8/FP8 全路径过一遍
- [ ] **动态 shape**：CUDA Graph capture 的 batch bucket 边界（恰好落在 bucket 切换点上的输入）
- [ ] **prefix caching 交互**：改动若触碰 KV 路径，开关 prefix caching 各测一遍
- [ ] **极端负载**：max-length 长输出、立刻取消的请求（abort）、空 prompt
- [ ] **回归测试**：跑 vLLM/vllm-ascend 仓库现有的相关单测套件，确保零回归

### 精度验证

- 数值类改动（量化、融合、reduction 顺序变化）必须做精度对拍：
  - 参考实现 vs 优化实现的输出逐 token 对比（logits 余弦相似度、top-1 一致率、KL 散度）
  - 容差标准写明：FP8 量化通常可接受 top-1 一致率 ≥99.5%（以具体任务基线为准，别拍脑袋）
  - 端到端验证：固定 seed greedy decode，对比生成文本的 diff
- 非数值类改动（调度、内存布局）只需功能等价测试

### 产出

- 测试记录：case 清单 + 每项 pass/fail + 精度对拍数据
- 若发现 bug：当天修完再进 Day 45，**不要带着已知问题提 PR**

## Day 46：项目 C 启动——实验设计

> 项目 C 的定位：**用受控实验证明你理解每个机制"何时有效、为何有效、代价是什么"**。这比"我知道 chunked prefill 是什么"高一个段位，是专家岗的区分度所在。

### 实验设计总原则

1. **单因子变量**：每组消融只动一个开关，其余全部冻结（模型、并发、数据集、随机种子、服务参数逐项核对）
2. **负载即自变量**：机制的收益强烈依赖负载分布，所以核心设计是"**开关 × 负载分布**"的二维矩阵，而不是单点开关对比
3. **先预测后实验**：每组实验先写下基于机制的预期（如"chunked prefill 在长 prompt 高并发下应显著降 TPOT p99，代价是吞吐略降"），再看结果验证——预测错了的地方就是你理解不到位的地方，恰恰最值得写进报告
4. **样本量**：每格至少 3 轮，报均值±方差

### 四组消融的详细设计

**通用固定配置**（建议）：Qwen3-8B，BF16 基线，`max_num_seqs=256`，其余参数默认；指标统一采集 TTFT p50/p99、TPOT p50/p99、吞吐（output tok/s）、goodput（如 TPOT p99 < 200ms 的 SLO 达标吞吐）、`/metrics` 中的引擎内部计数。

#### 消融一：chunked prefill 开关 × prompt 长度分布

- 自变量：
  - 开关：`--enable-chunked-prefill` 开 / 关（V1 默认开）
  - `max_num_batched_tokens`：2048 / 8192 / 32768（token budget 本身就是 chunk 粒度）
  - 负载：短（128-512 tok）/ 中（2k-4k）/ 长（8k-16k）三种 prompt 分布，输出固定 256 tok
- 关注指标：TPOT p99 的**抖动**（这是 chunked prefill 的核心收益）、TTFT 分布、总吞吐
- 机制预期：关掉后长 prompt 会独占整个 step，decode 被饿死 → TPOT 出现尖刺；开太小 chunk → prefill 拉长，TTFT 恶化
- 数据集：可用 `vllm bench serve` 的 random 长度分布或合成 ShareGPT 变体

#### 消融二：prefix caching 命中率梯度

- 自变量：
  - 开关：`--enable-prefix-caching` 开 / 关
  - 命中率梯度（关键设计）：构造共享前缀库，控制每个请求的前缀来自"全新"还是"已缓存"的比例，做出 0% / 50% / 90%+ 三档命中率
    - 实现：预生成 N 条长 2k 的系统前缀，请求按比例从池中抽取复用或随机生成
- 关注指标：TTFT（应随命中率单调下降）、prefix cache hit rate（`/metrics` 里的 `gpu_prefix_cache_hit_rate`，用于验证梯度构造成功）、KV 显存占用
- 机制预期：命中一个 2k 前缀 ≈ 省掉 2k token 的 prefill 计算 + KV 写入；同时观察 cache 管理开销（hash/引用计数）在高换入换出下的代价
- 陷阱提示：GQA/多模态 hash 语义、block 对齐导致部分命中——报告里要讨论"命中率与收益不是线性"的原因

#### 消融三：投机解码接受率-收益曲线

- 自变量：
  - 引擎：EAGLE-3 或 MTP（模型可得性决定），关 / 开
  - `num_speculative_tokens`：1 / 2 / 3 / 4
  - 负载（决定接受率）：代码补全（HumanEval 类，高接受率 ~80%）vs 开放对话（ShareGPT，低接受率 ~40-60%）
- 关注指标：TPOT（ms/token，注意换算成"每个被接受 token 的有效时延"）、接受长度分布（`/metrics` 的 acceptance rate）、吞吐
- 机制预期：加速比 ≈ f(接受率, 草稿成本)，理论曲线自己先推（Week 4 Day 25 的公式），实验点叠上去验证；重点捕捉**负收益失效模式**——低接受率 + 深草稿下验证开销超过节省
- 对照理解：这就是"用计算换访存"——decode 是访存 bound，多算几个 token 几乎免费，只要能被接受

#### 消融四：量化吞吐-精度权衡

- 自变量：
  - 精度档位：BF16 基线 / W8A8（或 FP8 权重+激活）/ W4A16（AWQ 或 GPTQ）/ FP8 KV cache 叠加
  - 注意和你的昇腾量化算子经验打通：同一档位在 GPU GEMM 上的收益结构 vs 昇腾 Cube 的收益结构
- 关注指标：吞吐（权重小→同显存更大 batch→吞吐升）、显存占用、并发上限变化、精度（困惑度 + 3-5 个基准任务得分 + 生成质量抽查）
- 机制预期：decode 是访存 bound → 权重量化收益直接体现在 TPOT；prefill 计算 bound → 量化对 TTFT 收益有限（甚至因反量化开销略慢）；KV 量化同时改善容量与 TPOT，但注意 attention 精度敏感性
- 这组实验直接复用 Week 4 Day 23-24 的部署和脚本

### 压测脚本与指标采集流水线

- 写一个统一的 runner（伪代码）：

```bash
# ablation/run.sh <group> <case> <seed>
# 1. 用对应参数启动 vllm serve（参数从 cases.yaml 读取）
# 2. 等健康检查通过 + warmup
# 3. vllm bench serve --seed $SEED ... --output-json results/<group>/<case>_$SEED.json
# 4. 抓取 /metrics 快照存盘
# 5. 停服，冷却 30s
```

- 所有 case 参数收敛到一个 `cases.yaml`，结果统一落 `results/<组>/<case>_<seed>.json`
- Grafana 看板最少四张图：TTFT/TPOT 分位数时序、吞吐时序、KV block 使用率、preemption/queue 计数（跑实验时人盯一遍，经常能发现脚本没设计到的现象）

## 附：本周常见坑

1. **对比实验换着数据集跑**：baseline 用 ShareGPT、优化版用 random——数字再好看也是自欺。全部配置进版本控制。
2. **只报均值不报分位数**：chunked prefill 的收益主要在 p99 尾延迟，只看均值会得出"没提升"的错误结论。
3. **消融实验跑成"配置扫描"**：只罗列数字不讲机制，等于把解释权交给面试官。每格数据都要回答"为什么"。
4. **PR 描述只贴数字**：reviewer 最想看的是 why 和取舍，数字只是证据。
5. **赶进度跳过精度验证**：性能 PR 引入精度回归会被直接打回，Day 44 不能省。
